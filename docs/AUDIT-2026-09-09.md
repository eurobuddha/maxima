# Parlons family audit — 9 September 2026

Decentralisation was a blocking requirement throughout this audit. The changes retain independent relay operators, user-selected bootstrap relays, signed directory records, redundant discovery, local custody, and classic Maxima interoperability. They introduce no mandatory publisher service, telemetry, hosted identity provider, new protocol authority, or new production dependency.

This is an engineering audit and remediation record, not a certification that every source line is defect-free. The family was mapped across all variants; detailed review concentrated on transport, directory availability, chat delivery, account persistence, wallet counters, device pairing, the shared panel and its desktop integrations. Tests use temporary state and synthetic identities. No funded transaction or fleet deployment was used. Following the owner's authorization, iOS builds through 0.1.25 build 23 were installed and launched on the connected iPhone. The 0.1.20 startup log also confirms relay attachment, push registration and history catch-up; this is not full end-to-end feature validation.

## Most consequential fixes

### High: file-backed wallet counters could treat damaged state as unused keys

The existing Cloud counter reader caught errors and returned zero. The standalone desktop also had a separate implementation of the same persistence responsibility. Treating unreadable, empty or malformed counter state as an unused signing key is unsafe for one-time signatures.

The Cloud implementation is now the shared donor in `walletfile/com/eurobuddha/wallet/FileKeyUses.java`. `cloud/src/main/java/com/eurobuddha/maxima/cloud/CloudKeyUses.java` and `desktop/src/main/java/com/eurobuddha/maxima/desktop/wallet/DesktopKeyUses.java` are thin host adapters. The existing file names, namespaces and properties format remain compatible. Both mirrors are read under the existing JVM/directory and file locks; counts only increase, and reservations are flushed before a leaf is returned. Existing unreadable, empty, malformed, negative or overflowing state now stops the operation. A missing file still permits first use.

The Android donor `walletshared/com/eurobuddha/wallet/PrefsKeyUses.java`, the wallet engine and sibling PandaPools counter implementation/tests were inspected. They use different persistence/remote reservation contracts and were not substituted for this file-backed implementation. The full-node hosts continue using the embedded Minima wallet's counter system.

`walletfile-test/com/eurobuddha/wallet/FileKeyUsesTest.java` runs in both Cloud and desktop: malformed/unreadable state, legacy compatibility, mirror write failure, monotonic imports, exhaustion and concurrent reservations. Three cases fail against the original Cloud implementation; all six pass against the shared implementation in each host. A failed reservation can waste a leaf; it must never reissue one. This does not prove resilience against arbitrary filesystem rollback or malicious local tampering.

### High: account authorisation could diverge from persisted state

`account/src/main/java/com/eurobuddha/maxima/cloud/DevicePairing.java` could acknowledge changes whose file write had failed. It now reports persistence failure and restores the previous in-memory authorisation/pending snapshot. Corrupt existing state fails startup instead of silently becoming an empty account. Bootstrap code reads, writes and consumption also fail explicitly; a code is consumed before authorisation is persisted, so a failed save can require minting a new code but cannot leave that code reusable after a successful authorisation.

The existing backup writer became `account/src/main/java/com/eurobuddha/maxima/cloud/AccountFiles.java`: write a private temporary file in the same directory, flush it, then replace the target. POSIX systems create the temporary file with mode 0600. `AccountBackup` and `cloud/src/main/java/com/eurobuddha/maxima/cloud/Tenants.java` reuse it. The atomic-move fallback applies only when the filesystem reports that atomic moves are unsupported; that fallback is not a power-loss guarantee.

Unauthenticated pending device requests are bounded at 64, labels at 256 characters, and identical retries avoid repeated writes. A valid owner bootstrap code can still pair when the pending queue is full. Five persistence regressions fail against the original implementation and pass with the fix in `cloud/src/junit/java/com/eurobuddha/maxima/cloud/DevicePairingPersistenceTest.java`.

### High: local admin RPC lacked browser-origin checks

`node/src/main/java/com/eurobuddha/maxima/node/AdminRpc.java` still binds to loopback. It now validates the exact local Host/port, rejects foreign or null Origins and inappropriate Fetch Metadata, limits methods to GET/POST, and shuts down its executor on stop. `node/src/test/java/com/eurobuddha/maxima/node/AdminRpcTest.java` uses empty commands and temporary loopback sockets to verify allowed and rejected requests.

This is protection against browser-origin misuse, not local-user authentication: trusted local processes retain access. No admin endpoint was exposed publicly, and no new remote authority was introduced.

## Continuation: RPC lifecycle repair

`MaximaNode.stop()` previously left `RpcPeer`'s reply executor alive and its requests pending. Repeatedly replacing accounts/connections could retain reply workers and callbacks until an unrelated timeout path ran; the old peer also continued accepting calls after its owner stopped.

`RpcPeer` now implements `AutoCloseable`. Registration and close share a lifecycle lock; close marks the peer closed, shuts down queued reply work and conditionally removes each pending entry before failing it. Callbacks execute outside the lock, and a failing callback cannot strand the other requests. New calls reject, new inbound RPCs are ignored, and queued reply tasks check the closed state. `MaximaNode.stop()` owns this cleanup. A write already in progress can still finish; interruption is not a rollback of a remote operation.

`core/src/junit/java/com/eurobuddha/maxima/core/rpc/RpcLifecycleTest.java` exercises the real node owner with synthetic identities and a fake attached transport: pending-call cleanup despite a throwing callback, rejection after stop, and interrupted workers/discarded queued replies. All three tests fail against the original source and pass with the repair. The rebuilt Node jar's RPC/node class files were compared against the tested compiled classes. No relay selection, bootstrap, wire format, service authority or signing algorithm changed.

The full goal remains active. Account worker ownership and keyed-lane shutdown were addressed in the later continuation below. Queue bounds and wake response handling still need further work; the later relay-lifecycle continuation addresses in-flight attachment ownership.

## Continuation: payment retries and counter completion

### Major: rejected payment amounts consumed the retry ID

`ParlonsControl` recorded the `wallet.send` / `wallet.buildsend` request ID before parsing and rejecting a zero amount. Repeating the rejected request then returned `building`; correcting its amount with the same ID could also acknowledge work that was never queued. Both handlers now reuse `chat.pay`'s validation-before-reservation ordering. Valid duplicates still use atomic `putIfAbsent` and cannot queue another payment within the existing retention window.

`cloud/src/junit/java/com/eurobuddha/maxima/cloud/PaymentRetryTest.java` covers both handlers through authenticated local dispatch with a synthetic wallet: repeated invalid requests stay rejected, corrected retries execute once, and valid duplicates remain suppressed. All four cases failed against the original source and pass with the repair. No transaction was signed or broadcast. This repair does not make the existing in-memory payment-ID cache durable across process restarts or extend its 30-minute retention.

### Major: counter adjustments reported success before persistence

`ParlonsControl` immediately reported the requested count while its write was still queued. Both its worker and the `ParlonsCore` adapter swallowed write failures. Fractional and overflowing numeric inputs could also be truncated to a different integer by `Number.intValue()`.

The shared handler now validates an exact integer, keeps the write on the ordered wallet lane and reports success only after the adapter returns and the counter reads back at least the requested value. Adapter exceptions reach the caller. A slow write returns a poll key after the existing Terminal handler's 300 ms completion leash. A single in-flight counter job is retained; same-target retries share it, other targets receive a busy error. Retrying a pending write avoids reading behind that writer's file lock. Ordinary counter reads retain their existing persistence path.

`ParlonsRemote.walletUses()` reuses the Terminal SDK's bounded polling pattern. Pending replies deliberately carry `ok:false` plus an explanatory error so older clients cannot display “Counter raised” before completion. New clients poll the key for up to the polling deadline; an individual network RPC still has its existing timeout/re-resolution behavior. Timeout or interruption does not cancel the monotonic counter write. A later request can refresh the saved value. Only the latest counter job is retained; polling a superseded key returns an explicit refresh instruction.

`cloud/src/junit/java/com/eurobuddha/maxima/cloud/WalletUsesTest.java` covers persisted success, write failure and recovery, blocked-write retries/polling, and invalid numeric admission. The initial four regressions all failed against the original source. Final tests also verify that a retry avoids a blocked counter read and a repeated completed target causes no extra write. The adapter and SDK changes were reviewed with the portal caller, compiled in the affected host builds, and checked for propagation in both jars. End-to-end device/network counter adjustment was not exercised.

The repairs use the existing account module; no runtime service, authority, dependency or protocol discovery rule was added.

## Continuation: account worker shutdown

### Major: stopped accounts retained executors and queued work

`ParlonsCore.shutdown()` stopped its maintenance pump, local panel and node, but left the control channel's send/media/call/push/console executors, optional wake worker, wallet upkeep worker and host attachment worker open. `SerialLanes.shutdownNow()` stopped only the underlying pool: its own per-key queues survived, so a running task that caught interruption could continue into queued operations. A refused or null task could also leave a key with no runner and silently strand later submissions.

`ParlonsControl` now owns an idempotent `close()`: refuse new requests (including pairing), stop owned executors, discard queued keyed work, stop wake admission, detach the local event sink and release transient caches. Pending counter/console responses report closure and possible completion of running work. Push/call callbacks handle closure races. Profile re-announcement uses the existing send lane instead of creating an unmanaged thread per rename.

`ParlonsCore.shutdown()` calls this cleanup and stops wallet/host workers. Wallet opening now uses the existing wallet executor and checks whether the account is still running before publishing readiness or starting upkeep. Startup and shutdown are serialized; a closed runtime cannot restart or adopt another relay, and a failed startup invokes cleanup. This serialization means shutdown waits for an already-running startup to return; its existing network connection leashes still apply.

`SerialLanes` guards queue admission and closure together, clears per-key queues on stop, rejects every later submission, and rejects null tasks before mutating the lane map. `WakeProxyClient` also serializes admission with close, stops its executor and preserves interruption. The wake proxy remains optional and device-selected.

The three added `SerialLanesTest` cases and the first two `AccountLifecycleTest` cases all failed against the original code. Three additional account tests verify that a queued payment never reaches the synthetic wallet after stop, a delayed wallet open does not publish readiness/start upkeep, and a stopped runtime cannot restart or adopt a relay. Existing wake, payment and counter tests remain green. The full family gate passes **244 JVM tests** and **63 wire vectors**, plus Android, portal and JVM packages. Tested class files were compared byte-for-byte inside both account-host jars.

### Limits and next work

Already-running operations may finish; interrupting a worker is not a rollback of signing, broadcasting or a console command. This repair does not add durable queue replay or prove that every in-flight socket has stopped when shutdown returns. Source review found a separate `HostPool.attachOne()` / `closeAll()` race: an attachment finishing after the active-host snapshot can be inserted into the closed pool. The following transport continuation reproduces and repairs that race in Java and Swift. The account's still-unbounded work queues and the wake client's unused response-body buffering also remain under review.

Review verdict for this worker-ownership change: approve within the stated scope. Relay choice, independent operation, wire format, custody and signing algorithms are unchanged. The whole-family audit remains active.

## Continuation: pending relay attachments

### Major: closed pools could acquire new connections

Java and Swift `HostPool.closeAll()` closed only connections already in the active map. An in-flight handshake could finish afterward and insert its socket into the closed pool. Both implementations also allowed concurrent attempts for the same host, replacing the first connection without closing it. Java `HostConnection.attach()` could create a fresh socket after that connection instance had already been closed.

Both pools now register pending connections under a lifecycle lock before dialing. Only one attempt per host is admitted; completing an attempt can publish it only while it still owns that registration and the pool remains open. Shutdown drains active and pending connections, refuses future attempts and closes sockets outside the pool lock. Deliberate detach also cancels pending work, without counting the cancellation as a relay failure. Java connection instances own one socket and cannot reopen after closure; reader startup also checks closure.

The implementation reuses the Java account/RPC closure pattern, Swift's existing remove-under-lock/close-outside-lock pattern, and the existing `FakeRelay` / `AckRelay` fixtures with held greetings. Four Java tests and three Swift tests failed against the original sources. The final suites add deliberate-detach and Swift duplicate-attempt cases, giving five lifecycle tests in each language. The Java detach case also verifies immediate retry. Fixtures use loopback and synthetic identities only.

## Continuation: Swift cancellation and transport cleanup

### Major: cancellation could return success and retain pending work

`ParlonsKit/Sources/ParlonsKit/Session/TcpLink.swift` used unstructured tasks for `withTimeout`, but its comment incorrectly claimed caller cancellation was inherited. Cancelling a caller did not promptly release it or cancel cooperative work, and an already-cancelled caller could still run the operation and receive success. A completed operation also left its timer sleeping until the deadline.

The existing `ResumeOnce` now owns the operation/timer handles and records the first completion even before its continuation is armed. Completion cancels and releases the owned tasks before resuming the caller. Cancellation and deadlines still return without waiting for a body parked on a non-cooperative continuation; resource owners remain responsible for releasing that continuation.

`RpcPeer.call` removes its waiter and cancels its detached send task when the call exits. Registration and cleanup use the same lock, and registration checks cancellation. Attached sends retain the existing ACK tombstone after cancellation, preventing a late ACK from answering another send. Cancelled relay attachments cannot enter the pool or penalise a relay. Cancelled RPCs are propagated instead of entering the ordinary resolve-and-retry path, and the maintenance pump checks cancellation after sleep.

### Major: abandoned TCP reads could remain on a reusable stream

A timed-out `TcpLink.readExactly` returned while its receive continuation could still consume bytes later. It now closes on error/cancellation; the abandoned body checks cancellation before appending bytes. Connect admission, readiness and closure share a lock, and a link instance starts once. Async write cancellation closes its socket. These changes do not cancel an already-sent remote command or reverse its effects.

## Continuation: Java send interruption

### Major: interrupted sends lost the worker's stop signal

`core/.../net/HostConnection.send` caught interruption of its ACK wait through a generic exception handler. `CompletableFuture.get` clears the thread interrupt status when it throws, so the owning worker could continue as if no stop had been requested. An already-interrupted thread could also enqueue/write a frame before reaching that wait. `MaximaSender.send` could invoke an attached transport or begin a fresh-socket fallback despite an existing interrupt.

Attached sends now check interruption before building/enqueuing and again after acquiring the send lock. Interrupted ACK waits restore the flag and retain the existing waiter position, so a late ACK cannot answer the next send. The shared sender checks interruption before invoking an attached transport and before falling back to a fresh socket. This reuses the interrupt-preservation pattern already present in `WakeProxyClient`; no protocol or routing change is involved.

All four `SendInterruptionTest` regressions failed against the original source. They cover the restored flag, late-ACK ordering, no frame from an already-interrupted sender, refusal before invoking an attached transport, and refusal before fresh fallback. The existing loopback `FakeRelay` now exposes a message hook, following the held-ACK server tests. Synthetic identities and sentinel transport inputs avoid any real-account send.

Interruption is cooperative admission/ACK-wait cancellation, not a rollback: a frame already written can still be delivered. This does not make a blocking Java socket connect/write immediately interruptible; the owning connection's closure and existing socket timeouts still govern those operations. Review found no blocking issue in this change. The equivalent Swift cancellation handling is included in iOS **0.1.17**.

## Continuation: Swift RPC peer shutdown

### Major: a stopped device node continued accepting and retaining RPC work

`ParlonsKit/Sources/ParlonsKit/Session/DeviceNode.swift` closed its relay pool but did not close its RPC peer. `RpcPeer` had no closed state: retained references could submit calls and dispatch inbound requests after stop, pending calls remained until their deadlines, service handlers could launch replies after their owner stopped, and reply tasks had no lifecycle owner. `ParlonsRemote.close()` failed pending callbacks with a generic transport error, allowing its ordinary RPC recovery path to retry an intentionally closed session.

The repair ports the existing Java `core/.../rpc/RpcPeer.java` lifecycle and its `RpcLifecycleTest.java` cases. Swift reuses its own lock-based pending registration, task cancellation, `Box` and `ResumeOnce` fixtures. The RPC peer now owns its send, service and reply tasks; close marks admission closed under the same lock, clears pending calls and routing references, then cancels tasks and resumes callers outside the lock. Repeated closure is harmless. Address/attached-sender access is synchronized, and setters cannot revive a closed peer. A late service completion cannot enqueue replies after closure.

`DeviceNode.stop()` closes the peer before its pool. `ParlonsRemote` preserves the typed local `RpcError.closed` through both RPC attempts, and checks peer state before looking up the live address.
