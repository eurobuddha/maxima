# Candidate-bearing call setup — 13 September 2026

Original Android 0.6.127, Cloud Android 0.2.76, Node 0.2.112 and Cloud host 0.11.108 gather initial ICE candidates into the offer/answer before sending. minimaCore Desktop 0.16.86 and minimaDesk 0.7.69 pin that node and receive the same shared-panel change. iOS has no calling engine and is unaffected; standalone Swing still has signalling-only calling, so this is not a standalone media implementation.

## Problem and evidence

The owner reported one successful external video call and no successful voice calls, initially on 0.6.125; the captured answered failure had both Android phones on 0.6.126. The Fold accepted the answer and its SDP, then received host/public ICE about five seconds apart. The public candidate arrived 10.683 seconds after the answer; the peer sent bye 5.312 seconds later. This establishes a post-answer connection failure, not its complete root cause. Far-end logs were unavailable.

A local transport reproduction reuses LanPeerTest synthetic identities and DirectEndpoint. One five-second failing route before a working route delays separate answer, host ICE and public ICE to 5.140, 10.177 and 15.211 seconds respectively. This confirms that the existing serial signal queue and redundant per-address fanout can consume setup time despite a working route. It does not prove the friend's exact route/NAT conditions.

## Change and reuse

The existing CallManager and PortalCallManager keep their call identity guards, encrypted signal schema, remote-SDP/ICE ordering, fleet STUN servers and 20-second connecting timeout. The shared Android GatheredCallSdp helper waits for local-description success and ICE gathering completion, capped at 1500 ms. It sends the current native localDescription, including gathered candidates, in one existing offer/answer message. Later candidates continue through the existing ICE messages. Calls ended while gathering cannot publish a stale offer.

The shared browser engine uses the equivalent bounded gathering step. WebRTC's current local description includes gathered candidates ([W3C WebRTC specification](https://www.w3.org/TR/webrtc/)); no custom SDP construction, new signal kind or new dependency is introduced. Candidate comparison is scoped to its media section and accounts for the trickle-only ufrag extension, so already-embedded candidates do not fill the signal queue again. Genuine late candidates remain supported. Native local SDP failures now terminate with an explicit preparation error rather than sending an invalid offer.

## Validation

Passed 19 original Android tests (including seven new helper regressions), 18 Cloud Android tests, 22 panel JavaScript tests, 7 minimaCore host tests and 6 minimaDesk host tests. Signed Android release builds and release-vital lint passed. A real Chromium harness verifies two-way voice/video RTP, hidden ringtone, Answer/Hangup and light/dark rendering with a five-second delay for every signalling message. The final implementation sent only candidate-bearing offer, answer and bye for each tested call; the old implementation queued separate candidates. Both versions can connect on this local network: this is compatibility/regression evidence, not independent-internet success.

The S10+ native check passed: two real WebRTC peers connected using only candidate-bearing offer and answer. The isolated filescheck app tests the production helper using two native Android peers with data-channel ICE/DTLS, no chat identity, microphone, camera or STUN service. Its source import now copies only the Android-compatible torrent suite actually used by MainActivity; the separate JVM-only file-manager tests remain unchanged.

## Decentralisation and deployment limits

The change reduces separate setup messages and their queue delays. It preserves every advertised relay route, signed/encrypted signalling and direct encrypted media. There is no new central service, no Google STUN, no TURN service or forced server, and no changed relay selection. The 1500-ms cap plus continued trickle mitigates slow or missing STUN responses. The existing fleet's operator concentration and paused WakeProxy centralisation are not resolved; full decentralisation is not claimed.

Both participants should update for a useful retest; existing peers can parse candidate-bearing SDP, but only the updated side batches its outgoing candidates. Cloud clients also need their paired node updated. No fleet service was deployed by building or publishing these jars. New Mac candidates require final notarization/stapling before desktop store/feed publication; Apple upload approval remains pending from the preceding publication task. A successful call over the owner's two actual internet connections is still required before declaring the external voice failure fixed.
